GymBuddy is a standalone mobile app: a Vite + React single-page app bundled into a Capacitor shell (Android now, iOS later) that talks directly to the project's own Supabase. There is no app server and no Lovable dependency.

GymBuddy uses separate typed routes for Welcome, Onboarding, Home, and Workout. Why: each step remains directly revisit-able.

- Data API lives in `src/lib/gym-api.ts` and `src/lib/account-api.ts`; every call takes `{ data }`. Reads query tables directly under RLS; writes call SECURITY DEFINER functions in `supabase/migrations/*_standalone_api.sql` that act as `auth.uid()`. Why: tables only grant members SELECT, so all writes stay server-validated without an app server.
- Never add a function argument that names a user or decides Pro access; the database derives both. Why: the client is untrusted.
- Pre-made plan rotates via `users.next_split_day` (A→B→C→A, advanced in `complete_workout`); Home and Workout share the split-day query for equipment, ordered exercises, and targets. Why: both screens stay consistent.
- Workout `mode` selects premade or custom independently. Why: a custom routine must not hide the guided plan.
- Home blocks only browser Back; Android Back on Welcome/Auth/Home minimizes the app (`NativeBridge`). Sign Out clears protected caches and replaces history. Why: avoid stale protected screens without trapping the member.
- Auth emails redirect to `app.gymbuddyapp.gymbuddy://auth-callback/...` on phones (`authRedirectUrl`); `NativeBridge` turns the link into a session. The URL must be in Supabase Auth → Redirect URLs. Why: links must reopen the app, not a browser.
- Login sessions are stored with Capacitor Preferences on phones, and data a member must never lose (offline set queue, workout in progress, cached profile, offline data cache) goes through `src/lib/durable-storage.ts`, loaded before first render. Why: the OS may clear WebView storage.
- Account data on the phone belongs to one account (`src/lib/device-owner.ts`): any new per-account key goes in `ACCOUNT_DATA_KEYS`. It is erased when a different account signs in, or the account is deleted; plain sign-out keeps it so waiting sets upload when the same member returns. Why: a shared phone must never upload one member's sets to another's account.
- Abandoning a workout goes through `abandonActiveSession` (queues deletion of its saved sets); `delete_workout_set` never touches sets of a finished workout. Why: abandoned sets must not count, and a stale phone copy must not damage history.
- The rest timer mirrors into a native Android short foreground service (`RestTimerService.java`, via `src/lib/native-workout.ts`): live lock-screen countdown and an on-time alert, silent if the app is on screen. Don't switch it to scheduled notifications. Why: Android 14+ denies exact alarms by default, so scheduled alerts arrive about a minute late, and requesting them opens system settings mid-workout.
- Haptics and keep-awake go through `src/lib/native-workout.ts`. Why: `navigator.vibrate` and the Wake Lock API are ignored in the iOS/Android WebViews.
- Home, History, and Profile share the bottom tabs; Onboarding and Workout omit them. Why: avoid mid-session exits.
- Exercise cues live on exercise rows; completion totals only this session's log IDs. Why: guidance and totals stay accurate.
- Custom routine order lives in `custom_exercise_ids` and edits stay local until save. Why: drafts must not alter the active plan.
- Sets update optimistically, retry locally (`client_key` makes retries idempotent), and remain editable before Finish; the upload/retry rules live in `src/lib/set-sync.ts` (unit-tested), wired to the server by `set-sync-client.ts` and used by both the workout screen and `OfflineSyncWorker`; don't write a second sync loop. Don't rely on `navigator.onLine` alone: Android WebViews often report online with no signal, so failed uploads must fall back to "local". Why: poor gym connectivity must not corrupt stats.
- Bro Cards render on-device as 1080×1920 PNGs; saving/sharing goes through `src/lib/native-files.ts`. Why: personal workout metrics remain on-device, and WebViews can't download blobs.
- Pro access is `users.subscription_tier = 'pro'`, checked by `is_pro_user()` inside Pro database functions. Members cannot write that column; only future store-billing code (service role) may. Why: the paywall UI is cosmetic.
- Crash/error reporting goes through `src/lib/monitoring.ts` (Sentry, errors only). Never add emails, names or workout data to reports, breadcrumbs or extras; ids only, URLs without query strings. Why: this is personal health-adjacent data.
- Database changes go in a new file under `supabase/migrations/`; never edit an applied migration. Cover new or changed database functions and access rules in `supabase/tests/` (PGlite runs every migration as the real `anon`/`authenticated` roles). Why: the database is the only server, so its rules are the app's security.
- After adding a migration, run `npm run migrations:record` and commit the regenerated `supabase/record-applied-migrations.sql`; the member pastes it again after pasting the new migration. Why: the live database was built by hand-pasting, so it has no record of applied migrations, and a future `supabase db push` would re-run them all. A test fails if the file is stale.
- The app version is `package.json` "version" only: Android derives `versionName`/`versionCode` (1.2.3 → 10203) from it, and Sentry uses it as the release. Bump it for every store upload. Why: one number to keep in step.
- Weights are stored in kilograms everywhere (database, saved workouts, offline queue); kilograms or pounds is only what the member sees and types (`users.weight_unit`, `src/lib/weight-units.ts`). Show a weight with `formatWeight`/`formatVolume`, read a typed one with `parseNewSet`/`parseCorrection(…, unit)`, and use `useWeightUnit()` in a component; never write "kg" in text a member sees or divide by 2.2 yourself. Why: one stored truth, no rounding drift, no data migration.
- Accessibility: red text and icons use `text-destructive-text` (the solid `destructive` red is only for backgrounds and fails contrast as text); form outlines use `border-input`; every tappable control is at least 44 px (`min-h-11`, `size-11`) in both directions; every icon-only control has an `aria-label`; every overlay registers with `useBackToClose`. `src/lib/contrast.test.ts` reads the colour tokens in `src/styles.css` and fails if text or outlines lose contrast. Why: dark theme, gym lighting, one-handed use, TalkBack.
- Run `npm run check` (types, lint, tests, build) before pushing; CI runs the same plus an Android build. Lint checks code rules only; formatting is `npm run format`. Why: keep `main` shippable.
